# Golf App capability inventory

Discovery date: 29 October 2026. Source: `Simondarcy7/golf-scoring-app`, starting commit `2b46b8d9ba4ccb71cf10cd099ed7ff8a686c46df`. Target baseline: Blueprint `0d770675750ab62da417aee0fd230e9b7811415f`. Local donor fixes are tracked in the execution notes; they are not silently represented as committed provenance.

## Coverage and evidence

Surveyed the directory/file inventory of `mobile/src/{foundation,services,modules,hooks,components}` and selected release scripts. This covers the app's main implementation areas without reading every source file. Reviewed the implementation and/or tests listed below where marked **reviewed**. **Discovered** means a concrete source candidate, not a portability or quality verdict. **Existing** means a Blueprint counterpart exists; it still needs a behaviour comparison before replacement. This is not an exhaustive backend, game, data-pipeline or native-module audit.

The source currently uses Expo 58 / React Native 0.88; Blueprint's starter uses Expo 57. Extract pure contracts across this boundary; never copy dependency pins, native initialization or config plugins untested. `mobile/AGENTS.md` still points to SDK57 documentation. Provider/platform integrations need version-specific verification.

## Prioritization

Implemented locally: updates, telemetry lifecycle, durable outbox, draft recovery, staged import review, overlay focus recovery and engagement eligibility. Phase 2 composes the four UX/product packs in a runnable journal reference and fixes two donor fundamentals; see [phase 2 evidence](implementation-notes/phase-2-summary.md). Existing Blueprint primitives are not counted as newly implemented work.

Phase 3 reverse-adopts all four product workflow packs into Golf App and drafts/import-review into OddsBasket, with a shared fix propagated to both and focused identity/persistence regressions. See [the adoption record](implementation-notes/phase-3-summary.md) for published draft PRs, exact source evidence and coverage limits. Next acceptance priority is native/provider verification and review/merge of those revisions. Further extraction candidates include undo with new arrivals, notification preference transactions, contextual discovery and account recovery; inspect their full write/authorization contracts before promising generic complete features.

Do not infer portability from code volume. Rank candidates by repeated product need, preserved behaviour, dependency isolation, evidence quality and cost to adopt/maintain. No numerical reuse estimate is defensible yet.

## Important exclusions and remaining discovery

Golf scoring, handicaps, course matching, sporting rules, coaching content and map-specific calculations stay domain-owned unless a smaller general algorithm is independently useful. Native widgets, OCR/voice engines, games, backend migrations and course publishing need separate source and platform reviews. No third-party datasets, licensed assets, branding or production credentials were copied. This inventory is broader than the first implementation tranche; the status column prevents candidate discovery being presented as completed extraction.
